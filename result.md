# Результаты нагрузочного тестирования

## Краткий итог

Тест выполнен после перевода backend на **2 Uvicorn workers**.

| Показатель | Результат |
|---|---:|
| Виртуальные пользователи | 50 |
| Длительность | 2 минуты |
| HTTP-запросы | 2 690 |
| Пропускная способность | 20.85 RPS |
| Ошибки HTTP | 0% |
| Успешные проверки ответа | 100% |
| Медианная задержка | 1.76 с |
| p95 | 4.53 с |
| p99 | 5.20 с |

**Вывод:** система стабильно обслуживает запросы и не возвращает ошибок, но при 50 одновременных пользователях вычислительные endpoint’ы отвечают медленно. Целевой порог `p95 < 300 мс` не достигнут.

## Методика

Команда запуска:

```powershell
k6 run --vus 50 --duration 2m .\loadtest.js
```

Окружение:

- Docker Compose;
- backend: FastAPI + Uvicorn, 2 workers;
- PostgreSQL и Redis;
- активный ML forecast snapshot;
- полный стек: backend, frontend, ingest и ml-worker;
- нагрузочный генератор: k6.

Каждая итерация виртуального пользователя выполняла четыре запроса:

1. `GET /api/v1/forecast`;
2. `GET /api/v1/forecast/load`;
3. `GET /api/v1/forecast/analytics`;
4. `POST /api/v1/forecast/preview`.

После этого выполнялась пауза в одну секунду.

Тест проверял не только HTTP-статус, но и структуру JSON, наличие данных, `schema_version`, `meta.available`, дату и granularity.

Все проверки прошли успешно:


Проверены:

## Задержки по endpoint’ам

| Endpoint | Среднее | Медиана | p95 | p99 | Максимум |
|---|---:|---:|---:|---:|---:|
| `/forecast` | 2.35 с | 1.92 с | 4.70 с | 5.36 с | 5.92 с |
| `/forecast/load` | 2.40 с | 1.94 с | 4.75 с | 5.34 с | 5.96 с |
| `/forecast/analytics` | 2.38 с | 2.01 с | 4.76 с | 5.23 с | 5.35 с |
| `/forecast/preview` | 1.17 с | 1.13 с | 1.92 с | 2.30 с | 2.68 с |
| Все запросы | 2.07 с | 1.76 с | 4.53 с | 5.20 с | 5.96 с |

### Интерпретация

- **Медиана** показывает типичный запрос. Например, половина запросов к `/forecast` выполнялась быстрее `1.92 с`.
- **p95** означает, что 95% запросов завершились не медленнее указанного значения. Для `/forecast` это `4.70 с`.
- **p99** показывает хвост задержек. Каждый сотый запрос к `/forecast` занимал более `5.36 с`.

Самым быстрым оказался `preview`, потому что запрос ограничен одним маршрутом. Основные endpoint’ы dashboard (`forecast`, `load`, `analytics`) находятся примерно в диапазоне `2.3–2.4 с` среднего времени.

## Сравнение с предыдущим прогоном

Предыдущий тест выполнялся с одним worker’ом и ступенчатым ростом нагрузки до 50 VU в течение 10 минут. Он показал:

```text
RPS: 11.42

```

Новый тест с двумя workers и постоянными 50 VU показал:

```text

p95: 4.53 с
p99: 5.20 с
```

Сравнение не является полностью строгим, поскольку длительность и профиль нагрузки различаются. Тем не менее, два worker’а почти вдвое увеличили пропускную способность и заметно сократили хвост задержек.

## Возможные узкие места

Наиболее вероятные причины задержек:

1. Каждый worker независимо держит forecast snapshot в памяти.
2. Forecast-запросы выполняют расчёт строк, поправок и агрегации.
3. `load` и `analytics` дополнительно считают нормативы и статистику.
4. Сценарии читаются из PostgreSQL на каждом запросе.
5. Текущий k6-сценарий вызывает все четыре вычислительных endpoint’а в каждой итерации.

В реальном интерфейсе `preview` вызывается реже, чем в этом тесте, поэтому сценарий является достаточно тяжёлым смешанным профилем нагрузки.

Доля ошибок составила 0%, все проверки структуры ответов прошли успешно. Общий p95 составил 4.53 с, p99 — 5.20 с.
