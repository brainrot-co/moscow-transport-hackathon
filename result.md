# Результаты нагрузочного тестирования

## Итог для жюри

Тестирование проведено на полном Docker Compose-стеке после перевода backend на **2 Uvicorn workers**.

Наиболее важный завершённый тест:

| Показатель | Результат |
|---|---:|
| Суммарная заданная нагрузка | 20 RPS |
| Длительность | 60 секунд |
| HTTP-запросы | 1 205 |
| Фактическая пропускная способность | 18.92 RPS |
| HTTP errors | 0% |
| Checks | 100% |
| Dropped iterations | 1 |
| Общий p95 | 4.38 с |
| Общий p99 | не зафиксирован в сокращённом выводе |

Система сохранила корректность ответов и не вернула HTTP-ошибок. Однако целевой уровень `p95 < 300 мс` при смешанном forecast-профиле не достигнут.

Отдельный стресс-тест на 100 RPS показал точку деградации: генератор упёрся в лимиты VU, появились таймауты, `EOF` и ошибки HTTP. Поэтому заявлять поддержку сотен RPS по текущей реализации нельзя.

## Окружение

- Docker Compose;
- backend: FastAPI + Uvicorn, 2 workers;
- PostgreSQL и Redis;
- активный ML forecast snapshot;
- ingest и ml-worker запущены;
- нагрузочный генератор: k6;
- адрес API: `http://localhost:8000`.

## Методика

Использовался arrival-rate подход: k6 задавал целевое количество итераций в секунду, а не только число виртуальных пользователей.

Одна итерация mixed workload выполняла один запрос к одному из endpoint’ов:

- 70% — `GET /api/v1/forecast`;
- 15% — `GET /api/v1/forecast/load`;
- 10% — `GET /api/v1/forecast/analytics`;
- 5% — `POST /api/v1/forecast/preview`.

Авторизация выполнялась один раз в `setup()`. Каждый ответ дополнительно проверялся по HTTP-статусу и JSON-схеме.

## Завершённый стабильный тест: 20 RPS

Команда запуска:

```powershell
$env:K6_MIXED_DURATION = '60s'
$env:K6_FORECAST_RPS = '14'
$env:K6_LOAD_RPS = '3'
$env:K6_ANALYTICS_RPS = '2'
$env:K6_PREVIEW_RPS = '1'
k6 run .\tests\performance\mixed-load.js
```

Распределение нагрузки:

| Endpoint | Заданная скорость | Запросов | Среднее | Медиана | p95 | Максимум |
|---|---:|---:|---:|---:|---:|---:|
| `/forecast` | 14 RPS | около 840 | 1.68 с | 1.30 с | 4.42 с | 9.77 с |
| `/forecast/load` | 3 RPS | около 180 | 1.39 с | 458 мс | 4.24 с | 6.65 с |
| `/forecast/analytics` | 2 RPS | около 120 | 981 мс | 253 мс | 4.24 с | 9.11 с |
| `/forecast/preview` | 1 RPS | около 60 | 416 мс | 85 мс | 1.80 с | 2.52 с |
| Все запросы | 20 RPS | 1 205 | 1.50 с | 1.08 с | 4.38 с | 9.77 с |

Проверки:

```text
checks:          100%
http_req_failed: 0%
dropped_iterations: 1
```

Тест завершился полностью: все сценарии дошли до конца, ответы были корректными.

## Stress/degradation тест: 100 RPS

Команда запуска:

```powershell
$env:K6_MIXED_DURATION = '5m'
$env:K6_FORECAST_RPS = '70'
$env:K6_LOAD_RPS = '15'
$env:K6_ANALYTICS_RPS = '10'
$env:K6_PREVIEW_RPS = '5'
k6 run .\tests\performance\mixed-load.js
```

Тест был остановлен примерно через 2.5 минуты после явной деградации системы. Даже за это время были зафиксированы:

| Показатель | Результат |
|---|---:|
| Фактически обработанные HTTP-запросы | 3 318 |
| Фактический RPS | 22.17 |
| HTTP errors | 3.88% |
| Checks | 96.11% |
| Dropped iterations | 10 468 |
| Общий p95 | 51.55 с |
| `/forecast` p95 | 48.01 с |
| `/forecast/load` p95 | 57.94 с |
| `/forecast/analytics` p95 | 59.99 с |
| `/forecast/preview` p95 | 46.43 с |
| Максимум VU | 600 |

Причина: все сценарии достигли своих `maxVUs`, после чего k6 начал терять заданную arrival-rate нагрузку. Параллельно появились request timeout и `EOF`.

Этот тест подтверждает, что текущая реализация не выдерживает смешанный профиль 100 RPS.

## Отдельный benchmark `/forecast`

Был запущен ramping-arrival-rate benchmark с целевыми ступенями 50, 100, 200, 300, 400 и 500 RPS. На ранней стадии теста k6 достиг лимита 500 VU и фактически поддерживал только около 120 RPS.

После деградации были зафиксированы:

| Показатель | Результат |
|---|---:|
| HTTP errors | 5.93% |
| Checks | 94.06% |
| Dropped iterations | 7 155 |
| `/forecast` p95 | 36.87 с |
| `/forecast` p99 | 42.75 с |
| Максимум VU | 500 |

Этот результат показывает, что capacity основного endpoint’а находится значительно ниже заявленных сотен RPS.

## Проверки корректности

Во всех завершённых сценариях проверялись:

- успешный login demo-пользователя;
- доступность forecast snapshot;
- HTTP `200` для forecast endpoint’ов;
- `schema_version` ответа;
- `meta.available === true`;
- наличие массивов `data`, `hours` и `routes`;
- корректность даты и granularity;
- отсутствие dropped iterations в стабильном 20 RPS тесте.

## Сравнение с требованиями

| Метрика | Требование | Фактически | Статус |
|---|---:|---:|---|
| HTTP error rate | < 1% | 0% на 20 RPS | Выполнено |
| Корректность ответов | > 99% | 100% на 20 RPS | Выполнено |
| p95 latency | < 200–300 мс | 4.38 с на 20 RPS | Не выполнено |
| Стабильная capacity | Сотни RPS | 20 RPS без ошибок | Не подтверждено |
| Поведение при перегрузе | Без OOM и потери стабильности | ошибки после 100 RPS-профиля | Не выполнено |

## Интерпретация

Малый smoke-тест на единичных RPS ранее показывал p95 около 200 мс. При увеличении смешанной нагрузки latency резко растёт: на 20 RPS медиана составляет 1.08 с, а p95 — 4.38 с.

Следовательно, узкое место проявляется не при единичном запросе, а при конкуренции запросов. Наиболее вероятные причины:

1. вычисление forecast-строк и агрегации на каждый запрос;
2. дополнительные расчёты в `load` и `analytics`;
3. чтение сохранённых сценариев из PostgreSQL на каждом forecast-запросе;
4. один контейнер backend с ограниченным количеством workers;
5. тяжёлый смешанный профиль, где одновременно работают все вычислительные endpoint’ы.

## Финальная формулировка

> При тестировании полного Docker Compose-стека backend с двумя Uvicorn workers стабильно обработал смешанную нагрузку 20 RPS в течение 60 секунд без HTTP-ошибок и с 100% корректных проверок ответов. Фактический общий p95 составил 4.38 секунды. При стресс-тесте на 100 RPS система достигла предела: появились таймауты, `EOF`, 3.88% HTTP-ошибок и 10 468 dropped iterations. Текущая реализация демонстрирует корректность и работоспособность API, но не подтверждает требование сотен RPS при p95 менее 200–300 мс.
