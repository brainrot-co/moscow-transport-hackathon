Поправки к прогнозу: что общее для города, что для маршрута

Сейчас общегородские настройки лежат в карточке одного маршрута, и сохранение из карточки №50 незаметно меняет прогноз всего города. Ниже перечислено, что меняем, чтобы календарь и погода настраивались в одном месте для всего города, а ремонты и мероприятия — на своих маршрутах.

Версия от 27.09.2026. Основа: docs/corrections-spec.html, код ветки feature/fusion1. Формула применения поправок не меняется.

Решения

Что договорились

Один слайдер на фактор моделиПраздники и школьные каникулы: одно значение k на весь город и весь горизонт, без дат. Это меняет пример из спеки, где k сохранялся на 04.11.
Город: календарь и погодаФакторы модели и погодные события настраиваются на дашборде, на панели «Поправки по городу».
Маршруты: инфраструктураРемонт, укорочение, закрытие, мероприятие задаются в карточке маршрута. Событие может касаться нескольких маршрутов.
Особый маршрут — через сценарийЕсли праздник на №50 должен действовать иначе, диспетчер добавляет локальный сценарий «×1.3 на №50, 04.11». Отдельный k на маршрут не делаем.

Правило простое: то, что задают календарь или погода, одинаково для города; то, что связано с путями, площадкой или перекрытием, привязано к маршрутам. Бэкенд различает город и маршрут только по routes: null значит все маршруты.

Бэкенд

Изменения на бэкенде

Миграция схемы не нужна: таблица scenarios остаётся как есть. Нужна одна небольшая миграция данных и индекса (B1). Формула в corrections.py не меняется.

B1

Фактор модели: одна запись на фактор, без дат

обязательно
Проблема
P1, P3. Сейчас фактор модели создаётся через общий POST /scenarios с датами 2020–2100, дубли возможны.
Меняем
  • Новые эндпоинты: GET /model-factors (роль USER) и PUT /model-factors/{factor} (роль ADMIN). factor ∈ {holiday, school_holiday}, иначе 404.
  • PUT делает upsert одной строки kind='model_factor'. Даты сервер ставит сам (date_from=2000-01-01, date_to=2100-12-31), клиент их не передаёт. k = 1 тоже сохраняется как запись, не удаляется.
  • POST /scenarios с kind='model_factor' возвращает 422 use_model_factors_endpoint. Через /scenarios идут только сценарии.
  • _saved_corrections читает факторы модели отдельным запросом, без фильтра по датам запроса.
  • Миграция: схлопнуть существующие дубли (оставить строку с последним updated_at), добавить частичный уникальный индекс UNIQUE (factor) WHERE kind = 'model_factor'.
Файлы
api/v1/endpoints/model_factors.py (новый), crud/scenario.py, endpoints/forecast.py, endpoints/scenarios.py, alembic/versions/…
Тесты
два PUT подряд дают одну запись; POST с model_factor даёт 422; фактор применяется при любом date_from запроса.
GET /model-factors
[{"factor": "holiday", "value": 0.7, "updated_by": 3, "updated_at": "2025-11-01T10:12:00+03:00"},
 {"factor": "school_holiday", "value": 1.0, "updated_by": null, "updated_at": null}]

PUT /model-factors/holiday      {"value": 0.7}      // 0 ≤ value ≤ 2
→ 200 {"factor": "holiday", "value": 0.7, ...}
B2

Превью = сохранённые поправки + черновик

обязательно
Проблема
P2, P7. Когда поправки живут в двух местах, ни одна часть интерфейса не знает их все.
Меняем
  • POST /forecast/preview получает сессию БД и загружает сохранённые поправки так же, как GET /forecast.
  • Поверх накладывается тело запроса: model_factors заменяет сохранённые k по ключу; элемент draft с полем id заменяет сохранённый сценарий с этим id, без id добавляется как новый; exclude_ids убирает сохранённые сценарии из расчёта (удалённые или выключенные в черновике).
  • В draft разрешён только kind='scenario'.
  • Пустое тело даёт ровно тот же результат, что GET /forecast за тот же период.
Файлы
schemas/forecast.py, endpoints/forecast.py
Тесты
пустое превью совпадает с GET; draft с id заменяет, а не удваивает; exclude_ids убирает; model_factors из тела перекрывают сохранённые.
POST /forecast/preview
{
  "date_from": "2025-11-17T00:00:00+03:00", "date_to": "2025-11-23T23:00:00+03:00",
  "routes": [7], "granularity": "day",
  "model_factors": {"holiday": 0.5},                // необязательно
  "draft": [
    {"id": 41, "kind": "scenario", "factor": "route_shortened", "value": 0.6, ...},  // правка сохранённого
    {"kind": "scenario", "factor": "mass_event", "value": 1.2, "routes": [7, 17], ...} // новый
  ],
  "exclude_ids": [38]                                // сохранённый, но удалён в черновике
}

Фронтенд

Изменения на фронтенде

F1

Панель «Поправки по городу» на дашборде

обязательно
Проблема
P1, P4, P5. Городских настроек нет в одном месте.
Где
Новый компонент components/CityCorrections, открывается кнопкой на дашборде (боковая панель или модалка).
Состав
  • Праздники: один слайдер 0–2, шаг 0.1. Под ним список дней из GET /model-effects: «04.11 вт · модель закладывает −53% · при k = 0.7: −41%». Подсказка: «Включает переносы: рабочая суббота 01.11 +49% к обычной».
  • Школьные каникулы: такой же слайдер и список. Если все эффекты в пределах ±3%, показывать «модель почти не учитывает каникулы в этом периоде».
  • События по городу: форма с типами heavy_rain, heavy_snow, custom; даты, дни, часы, множитель, название. Сохраняется с routes: null. Список сохранённых городских событий с переключателем, правкой и удалением.
  • Превью по городу: POST /forecast/preview без routes, granularity: "day", на краткосрочный горизонт. График двух линий «Модель / Итог» по дням и сумма «было → стало».
  • Бейдж «Предпросмотр · не сохранено», кнопки «Сбросить» и «Сохранить». Сохранение: PUT /model-factors/… для изменённых факторов, POST/PATCH/DELETE /scenarios для событий.
  • Сообщение после сохранения: «Сохранено для всего города».
F2

Карточка маршрута: только события маршрутов

обязательно
Проблема
P1, P2, P7.
Убираем
Слайдеры праздников и каникул, saveModelFactor, factorIds, типы heavy_rain и heavy_snow из формы.
Меняем
  • Форма события: типы route_closed, route_shortened, mass_event, custom. Поле «Маршруты» с множественным выбором, текущий маршрут подставлен по умолчанию.
  • Список событий: сохранённые сценарии, где routes содержит этот маршрут. Если событие на нескольких маршрутах, показывать «также №17, №25».
  • Новый блок «Действует на весь город» (только чтение): факторы модели с k ≠ 1 и активные городские события, которые попадают в период графика. Ссылка «Изменить на панели города».
  • Превью по новой схеме B2: в draft только изменённые или новые события этой карточки (изменённые с id), в exclude_ids удалённые или выключенные сохранённые. model_factors не отправлять.
  • При пустом черновике не вызывать превью, а показывать rows из GET /forecast: там уже всё сохранённое. Это же убирает мигание при открытии (P7).
  • Сообщение после сохранения: «Сохранено для маршрута №7» или «для маршрутов №7, №17».

Бэкенд

  1. B1 и B2: без них разделение работает неправильно.

  3. B5: до мультивыбора маршрутов в F2.
  4. B4, B6: когда останется время.

  1. F6: общий справочник, мелкий подготовительный шаг.

Сценарии проверки

Данные активного прогона: «сейчас» 01.11.2025 03:00, краткосрочный горизонт до 31.12.

#ДействиеОжидаем
A1Панель города: праздники k = 0, превью04.11 по городу 112 тыс. → 237 тыс., 01.11: 197 тыс. → 132 тыс. Дашборд пока не изменился.
A2Сохранить A1Карта, общий график и топ обновились сразу. В карточке любого маршрута в блоке «Действует на весь город» стоит «Праздники k = 0».
