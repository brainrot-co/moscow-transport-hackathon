# Docker: что сделано и как запускать

Состояние на 27.09.2026. Прогнозный контур (ingest и ml-worker) поднимается одной командой и проверен с нуля: пустой том → загрузка истории → прогноз, совпадающий с сабмишеном.

## Файлы

| файл | что это |
|---|---|
| `docker-compose.yml` | сервисы `ingest` и `ml-worker`, общий том `tram-data`, лимиты ресурсов, заготовки для бэкенда и фронтенда |
| `compose.demo.yml` | демо «утро 1 ноября 2025»: часы стоят на 01.11.2025 03:00, быстрый опрос |
| `docker/ingest.Dockerfile` | образ приёма данных: Python, DuckDB, pandas, pyarrow |
| `docker/worker.Dockerfile` | образ прогноза: плюс torch (CPU) и chronos, справочники |
| `.dockerignore` | в образы не попадают данные, эксперименты, MLflow, документы |

## Как запустить

**Продакшен** (реальное время, данные приходят в `inbox/`):

```bash
docker compose up -d --build
```

**Демо** («утро 1 ноября 2025», прогноз на ноябрь–декабрь):

```bash
docker compose -f docker-compose.yml -f compose.demo.yml up -d --build
```

**Начальная загрузка истории** (один раз, на пустом томе; для демо — с тем же `-f compose.demo.yml`):

```bash
docker compose -f docker-compose.yml -f compose.demo.yml run --rm ingest python -m mtml.ingest load /dataset/train.csv /dataset/test.csv
```

**Сбросить всё** (том с фактами, прогнозами, часами и кэшем весов):

```bash
docker compose down -v
```

**Логи:**

```bash
docker compose logs -f ml-worker
```

## Образы

| образ | сжатый размер | что внутри |
|---|---|---|
| `tram-forecast/ingest` | 172 МБ | окружение 342 МБ: pyarrow 142, pandas 75, DuckDB 54 |
| `tram-forecast/ml-worker` | 428 МБ | окружение 1.3 ГБ: torch 2.14 CPU 652 МБ, transformers 115, pyarrow 142 |

- torch на Linux ставится **без CUDA** (индекс `download.pytorch.org/whl/cpu`, настроен в `pyproject.toml`), иначе образ был бы на гигабайты больше.
- Кэш uv вынесен в кэш-монтирование сборки и в образ не попадает.
- Зависимости разделены: база (ingest), группа `worker` (torch, chronos), группа `dev` (MLflow, графики, блокноты, тесты — в образы не идёт).

### ⚠️ Справочники зашиты в образ

В образ воркера копируются **только** `dataset/external/calendar.csv` и `dataset/external/school_holidays_moscow.csv`. **Обновить производственный календарь или каникулы можно только пересборкой образа воркера.** В контракте для этого предусмотрена папка `reference/` на томе — это следующий шаг, если понадобится обновлять справочники без пересборки.

Погода, события KudaGo, остановки из OSM и справочник организаторов в образ **не входят**: лучшая модель их не использует. Воркер теперь считает только признаки, которые запросила выбранная модель. Если через `ML_MODEL` включить модель с погодой или событиями, в образ придётся добавить и эти файлы.

## Замеры (Docker Desktop, Apple M5, контейнеры linux/arm64)

| что | значение |
|---|---|
| сборка ingest / воркера с нуля | ~15 с / ~65 с |
| начальная загрузка `train.csv` + `test.csv` (10 ГБ, 62 млн строк), 1 CPU / 2 ГБ | **3 мин** (локально без Docker — 52 с; разница — лимит в 1 ядро и чтение через общую папку Docker Desktop) |
| первый прогон воркера со скачиванием весов (~0.5 ГБ) | ~7 мин до ограничения потоков |
| прогон воркера (краткосрочный + 2 контрольных для поправок + годовой), 2 CPU | **3 мин 11 с**: один прогон Chronos 45–70 с на CPU (на M5 с MPS — 4 с) |
| пик памяти воркера | **651 МБ** из лимита 3 ГБ |
| память ingest в простое | 135 МБ |
| совпадение с сабмишеном | 14 639 из 14 640 строк; одна строка отличается на 1 посадку (округление x.5 на CPU против MPS) |

Ограничение потоков torch (`OMP_NUM_THREADS=2`, `MKL_NUM_THREADS=2`) обязательно: без него torch видит все ядра машины и под лимитом `cpus: 2` тормозит сам себя. Если воркеру дать больше ядер, эти переменные надо поменять вместе с лимитом.

## Переменные окружения

| переменная | сервис | продакшен | демо |
|---|---|---|---|
| `CLOCK_START` | оба | пусто (реальное время) | `2025-11-01T03:00:00` |
| `CLOCK_SPEED`, `CLOCK_END` | оба | 0, пусто | 0, пусто |
| `INGEST_POLL_SEC` | ingest | 60 | 5 |
| `INGEST_MEMORY_LIMIT` | ingest | 1GB | 1GB |
| `ML_MODEL` | воркер | `ensemble_cal_school_daytype_profile` | то же |
| `MIN_RERUN_MINUTES` | воркер | 60 | 2 |
| `WORKER_POLL_SEC` | воркер | 60 | 10 |
| `SHORT_RUN_AT` | воркер | 03:00 | 03:00 |
| `OMP_NUM_THREADS`, `MKL_NUM_THREADS` | воркер | 2 | 2 |

Часы записываются в `state/clock.json` **при первом запуске** и дальше из переменных не читаются. Чтобы перейти из демо в продакшен на том же томе, удалите том или этот файл.

## Известные особенности

1. **Архитектура.** Образы собраны на Apple Silicon (`linux/arm64`). На x86-машине жюри compose соберёт их сам при `--build`. Если нужны готовые образы под x86: `docker buildx build --platform linux/amd64 …`.
2. **Первый запуск воркера качает веса Chronos** (~0.5 ГБ) с Hugging Face в `/data/hf`. Без токена HF пишет предупреждение о лимитах — на работу не влияет. Дальше веса берутся из кэша.
3. **Время в логах** — часы контейнера (UTC), а «сейчас» системы — виртуальные московские часы из `state/clock.json`. В демо они расходятся на год, это нормально.
4. **Воркер на CPU медленнее** в 10–15 раз, чем на M5. Для прогона раз в сутки это не важно. Если понадобится быстрее: дать 4 ядра или отключить контрольный прогон для каникул (модель почти не учитывает каникулы, а он стоит 46 с).
5. **ingest при начальной загрузке** держится в лимите 2 ГБ благодаря сбросу DuckDB на диск (`/data/tmp/duckdb`, после загрузки пусто).
