# Docker: что сделано и как запускать

Состояние на 27.09.2026. Прогнозный контур (ingest и ml-worker) поднимается одной командой и проверен с нуля: пустой том → загрузка истории → прогноз, совпадающий с сабмишеном.

## Файлы

| файл | что это |
|---|---|
| `docker-compose.yml` | сервисы `ingest` и `ml-worker`, общий том `tram-data`, лимиты ресурсов, заготовки для бэкенда и фронтенда |
| `compose.demo.yml` | демо: виртуальные часы идут с 01.10.2025 до 04.11.2025 со скоростью 300, быстрый опрос |
| `docker/ingest.Dockerfile` | образ приёма данных: Python, DuckDB, pandas, pyarrow |
| `docker/worker.Dockerfile` | образ прогноза: плюс torch (CPU) и chronos, справочники |
| `.dockerignore` | в образы не попадают данные, эксперименты, MLflow, документы |

## Как запустить

**Продакшен** (реальное время, данные приходят в `inbox/`):

```bash
docker compose up -d --build
```

**Демо** (часы идут с 01.10.2025 03:00 в 300 раз быстрее реального времени и останавливаются 04.11.2025 03:00; водяной знак и прогноз едут вместе с ними):

```bash
docker compose -f docker-compose.yml -f compose.demo.yml up -d --build
```

**Стартовый прогноз** (`ml/seed/`, 2 МБ, запечён в образ ingest). На пустом томе ingest при старте раскладывает факты, календарь, справочник поправок и пару прогонов, посчитанную на тот водяной знак, который он получит в момент старта: для демо — cutoff 30.09 (старт часов 01.10.2025 03:00), для прода — cutoff 01.11 (реальное время, данных после 01.11.2025 нет). Прогноз на экране через ~7 с после `up`, загрузка истории для первого экрана не нужна. Воркер считает этот прогноз уже сделанным и пересчитывает при первом сдвиге водяного знака или ночью. Если пары на текущий знак нет (сменили `CLOCK_START`), стартовый прогноз не применяется и воркер считает сам.

Пересобрать стартовый прогноз (после смены модели, календаря, правил статусов дней или `CLOCK_START` демо; нужны факты в `data/actuals`):

```bash
uv run --group worker python ml/scripts/build_seed.py
```

**Полная загрузка истории** (нужна только если в прод будут приходить новые CSV: стартовый прогноз не содержит `raw/`, без него ingest пересчитает затронутые дни только по новым строкам):

```bash
docker compose run --rm ingest python -m mtml.ingest load /dataset/train.csv /dataset/test.csv
```

**Сбросить всё** (том с фактами, прогнозами и часами, а также база postgres со сценариями; после этого снова разложится стартовый прогноз):

```bash
docker compose down -v
```

**Логи:**

```bash
docker compose logs -f ml-worker
```

## Образы

| образ | сжатый размер | что внутри |
|---|---|---|
| `tram-forecast/ingest` | 164 МБ | окружение 342 МБ: pyarrow 142, pandas 75, DuckDB 54; стартовый прогноз 2 МБ |
| `tram-forecast/ml-worker` | 834 МБ | окружение 1.3 ГБ: torch 2.14 CPU 652 МБ, transformers 115, pyarrow 142; веса Chronos-2 ~0.45 ГБ в `/opt/hf` (без них образ был 428 МБ) |

- torch на Linux ставится **без CUDA** (индекс `download.pytorch.org/whl/cpu`, настроен в `pyproject.toml`), иначе образ был бы на гигабайты больше.
- Кэш uv вынесен в кэш-монтирование сборки и в образ не попадает.
- Зависимости разделены: база (ingest), группа `worker` (torch, chronos), группа `dev` (MLflow, графики, блокноты, тесты — в образы не идёт).

### ⚠️ Справочники зашиты в образ

В образ воркера копируются **только** `dataset/external/calendar.csv`, `dataset/external/school_holidays_moscow.csv` и `dataset/external/correction_factors.json` (справочник поправок, при старте воркер кладёт его в `reference/` на томе). **Обновить производственный календарь или каникулы можно только пересборкой образа воркера.** В контракте для этого предусмотрена папка `reference/` на томе — это следующий шаг, если понадобится обновлять справочники без пересборки.

Погода, события KudaGo, остановки из OSM и справочник организаторов в образ **не входят**: лучшая модель их не использует. Воркер теперь считает только признаки, которые запросила выбранная модель. Если через `ML_MODEL` включить модель с погодой или событиями, в образ придётся добавить и эти файлы.

## Замеры (Docker Desktop, Apple M5, контейнеры linux/arm64)

| что | значение |
|---|---|
| сборка ingest / воркера с нуля | ~15 с / ~65 с |
| начальная загрузка `train.csv` + `test.csv` (10 ГБ, 62 млн строк), 1 CPU / 2 ГБ | **3 мин** (локально без Docker — 52 с; разница — лимит в 1 ядро и чтение через общую папку Docker Desktop) |
| от `up` на пустом томе до прогноза на экране | **~7 с** (стартовый прогноз; раньше 8–10 мин: загрузка истории, скачивание весов, первый прогон) |
| скачивание весов при сборке образа воркера | ~70 с, один раз; при работе сеть воркеру не нужна (`HF_HUB_OFFLINE=1`) |
| прогон воркера на ансамбле `ensemble_cal_school_daytype_profile` (краткосрочный + 2 контрольных для поправок + годовой), 2 CPU | **4 мин 20 с**: основной прогон 2 мин 54 с, контрольные 1 мин 26 с на оба (замер 27.09). На одиночном Chronos было 3 мин 11 с |
| пик памяти воркера | **1.34 ГБ** из лимита 3 ГБ на ансамбле (651 МБ на одиночном Chronos) |
| память ingest в простое | 135 МБ |
| совпадение с сабмишеном | 14 639 из 14 640 строк; одна строка отличается на 1 посадку (округление x.5 на CPU против MPS) |

Ограничение потоков torch (`OMP_NUM_THREADS=2`, `MKL_NUM_THREADS=2`) обязательно: без него torch видит все ядра машины и под лимитом `cpus: 2` тормозит сам себя. Если воркеру дать больше ядер, эти переменные надо поменять вместе с лимитом.

## Переменные окружения

| переменная | сервис | продакшен | демо |
|---|---|---|---|
| `CLOCK_START` | оба | пусто (реальное время) | `2025-10-01T03:00:00` |
| `CLOCK_SPEED` | оба | 0 | 300: прогон ансамбля короче виртуальных суток, прогноз отстаёт от «сейчас» не больше чем на день |
| `CLOCK_END` | оба | пусто | `2025-11-04T03:00:00` |
| `INGEST_POLL_SEC` | ingest | 60 | 5 |
| `INGEST_MEMORY_LIMIT` | ingest | 1GB | 1GB |
| `ML_MODEL` | воркер | `ensemble_cal_school_daytype_profile` | то же |
| `MIN_RERUN_MINUTES` | воркер | 60 | 2 |
| `WORKER_POLL_SEC` | воркер | 60 | 10 |
| `SHORT_RUN_AT` | воркер | 03:00 | 03:00 |
| `OMP_NUM_THREADS`, `MKL_NUM_THREADS` | воркер | 2 | 2 |

Часы записываются в `state/clock.json` **при первом запуске** и дальше из переменных не читаются. Чтобы перейти из демо в продакшен на том же томе или сменить `CLOCK_*`, остановите ingest, ml-worker и backend и удалите `state/clock.json` вместе с `state/worker.json`: иначе в `worker.json` останется время прошлого прогона, и ночные пересчёты не сработают, пока часы его не догонят.

## Известные особенности

1. **Архитектура.** Образы собраны на Apple Silicon (`linux/arm64`). На x86-машине жюри compose соберёт их сам при `--build`. Если нужны готовые образы под x86: `docker buildx build --platform linux/amd64 …`.
2. **Веса Chronos запечены в образ воркера** (`/opt/hf`, `HF_HUB_OFFLINE=1`): интернет нужен только при сборке. Папка `/data/hf` на старых томах больше не используется, её можно удалить.
3. **Время в логах** — часы контейнера (UTC), а «сейчас» системы — виртуальные московские часы из `state/clock.json`. В демо они расходятся на год, это нормально.
4. **Воркер на CPU медленнее** в 10–15 раз, чем на M5. Для прогона раз в сутки это не важно. Если понадобится быстрее: дать 4 ядра или отключить контрольный прогон для каникул (модель почти не учитывает каникулы, а он стоит 46 с).
5. **ingest при начальной загрузке** держится в лимите 2 ГБ благодаря сбросу DuckDB на диск (`/data/tmp/duckdb`, после загрузки пусто).
