# Подключение бэкенда и фронтенда к прогнозному контуру

Для команд бэкенда и фронтенда. Полные схемы файлов — в `docs/ml-backend-contract.html`, поправочные коэффициенты — в `docs/corrections-spec.html`. Здесь — что конкретно сделать, чтобы подключиться.

## Главное в трёх пунктах

1. **Бэкенд ничего не вызывает у ML.** Прогнозный контур (`ingest` и `ml-worker`) сам пишет файлы на общий том `tram-data`. Бэкенд только читает их.
2. **Том подключается только на чтение** (`:ro`). Всё, что вводят пользователи (сценарии, поправки), бэкенд хранит у себя, не на этом томе.
3. **Системное время не использовать.** «Сейчас» для всей системы — в `state/clock.json`: в демо это 01.11.2025 03:00, а не сегодняшняя дата.

## 1. docker-compose

В `docker-compose.yml` в корне уже есть закомментированные заготовки. Раскомментируйте их и поправьте под себя:

```yaml
  backend:
    build: ./backend
    restart: unless-stopped
    environment:
      DATA_DIR: /data
    volumes:
      - tram-data:/data:ro
    ports:
      - "8000:8000"
    depends_on:
      - ml-worker

  frontend:
    build: ./frontend
    restart: unless-stopped
    ports:
      - "3000:80"
    depends_on:
      - backend
```

- Фронтенду том не нужен: он ходит только в API бэкенда.
- Бэкенду нужен только том. Портов ML-сервисов нет, HTTP между ними нет.
- В демо-режиме (`-f compose.demo.yml`) бэкенду ничего настраивать не надо: часы он читает из тома.

## 2. Что бэкенд читает с тома

Все пути — от `DATA_DIR=/data`.

| файл | что там | когда меняется |
|---|---|---|
| `active.json` | какие прогоны сейчас актуальны: `{"short": "<run_id>", "year": "<run_id>", ...}` | после каждого пересчёта |
| `runs/<run_id>/forecasts.parquet` | прогноз маршрут × час: `route, ts, yhat, q10, q90` | каждый прогон — новая папка |
| `runs/<run_id>/meta.json` | на каких данных и какой моделью, горизонт, маршруты без истории (`cold_start_routes`) | вместе с прогоном |
| `runs/<run_id>/effects.parquet` | эффекты праздников и каникул для слайдеров (только у краткосрочного) | вместе с прогоном |
| `actuals/actuals_hourly.parquet` | факт посадок маршрут × час | после каждой загрузки данных |
| `actuals/day_status.parquet` | статус дня маршрута (`final` / `partial` / `missing`), флаг `anomaly` | после каждой загрузки |
| `state/watermark.json` | до какой даты данные полные | после каждой загрузки |
| `state/clock.json` | «сейчас» системы | задаётся при первом запуске |
| `state/worker.json` | когда был последний прогон и последняя ошибка воркера | после каждого пересчёта |
| `monitoring/accuracy.parquet` | реальная точность прошлых прогнозов по горизонтам (1 / 2–7 / 8–30 / 31+ дней) | после каждого пересчёта |

Остальные папки (`raw/`, `inbox/`, `ingestion/`, `hf/`, `tmp/`) — внутренние, бэкенду не нужны.

## 3. Как бэкенд должен читать прогноз

**Держать в памяти, перечитывать по указателю:**

1. При старте прочитать `active.json`, загрузить `forecasts.parquet` и `effects.parquet` обоих прогонов (это ~100 тысяч строк, десятки МБ в памяти).
2. Раз в 30 секунд перечитывать `active.json`. Если `run_id` сменился, загрузить новый прогон **рядом со старым** и только после успешной загрузки переключиться.
3. Если загрузка не удалась (например, другой `schema_version`), остаться на старом и написать ошибку в лог.

Файлы прогона публикуются атомарно: папка появляется целиком, `active.json` меняется одним переименованием. Недописанных файлов бэкенд не увидит.

**Время:**

```python
import json
from datetime import datetime
from zoneinfo import ZoneInfo

clock = json.loads(open("/data/state/clock.json").read())
if clock["virtual_start"] is None:
    now = datetime.now(ZoneInfo("Europe/Moscow"))   # продакшен
else:
    elapsed = datetime.now(ZoneInfo("Europe/Moscow")).replace(tzinfo=None) - datetime.fromisoformat(clock["real_start"])
    now = datetime.fromisoformat(clock["virtual_start"]) + elapsed * clock["speed"]
    # если задан virtual_end — не позже него
```

## 4. Какие данные отдавать на каких видах

По договорённости с продуктом:

| вид в интерфейсе | шаг | откуда брать |
|---|---|---|
| прошлое (до водяного знака) | час, день | `actuals` — только дни `final`; дни `partial` показывать прогнозом |
| следующие сутки | час | краткосрочный прогноз (`active.json → short`) |
| следующая неделя | день и час | краткосрочный прогноз |
| месяц, год | день, неделя, месяц | краткосрочный, пока хватает его горизонта (61 день), дальше годовой (`active.json → year`) |

- Суммы по дням, неделям, месяцам и маршрутам — простое сложение `yhat`. Квантили `q10` и `q90` при суммировании не складываются: для сумм отдавайте только `yhat`.
- Маршруты из `cold_start_routes` (сейчас маршрут 5) — «нет данных для прогноза», а не ноль.
- Дни с `anomaly` в факте (ремонт, отмена) полезно подсвечивать.
- Свежесть: `watermark` и `published_at` из `active.json`. Если водяной знак отстаёт от «сейчас» больше чем на 3 дня — предупреждение «данные по состоянию на …».

## 5. Поправочные коэффициенты

Подробно — в `docs/corrections-spec.html` и `docs/corrections-status.md`. Коротко:

- Слайдеры «праздник» и «каникулы» работают через `effects.parquet`: `yhat × exp(log_effect × (k − 1))`, где `k` — положение слайдера (1 — как считает модель).
- Сценарии (ремонт, погода, мероприятие) — множители, которые бэкенд хранит у себя и применяет к часовым строкам до агрегации.
- ML-часть готова. Бэкенд (хранение сценариев, формула, предпросмотр) и интерфейс ещё не сделаны.

## 6. Что показать жюри из ML-контура

- `monitoring/accuracy.parquet` — «реальная точность прошлых прогнозов»: на наших данных краткосрочный прогноз даёт 0.89–0.90 на горизонтах до месяца.
- `meta.json` активного прогона — модель, дата данных, проверки качества.
- `state/worker.json` — когда был последний пересчёт.

## Частые вопросы

**Где взять данные, если том пустой?** Сначала начальная загрузка истории (одна команда, см. `docs/docker-status.md`). До этого `active.json` нет — бэкенд должен это пережить и показать «прогноз ещё не готов».

**Можно ли писать на том?** Нет. Том подключается `:ro`, писать туда может только ML-контур.

**Как понять, что прогноз обновился?** Сменился `run_id` в `active.json`.

**Почему даты в демо — 2025 год?** Демо показывает систему «утром 1 ноября 2025»: часы берутся из `state/clock.json`, а не из системного времени.
